# Codex Session Observation Decoupling

5 October 2026

## Context

The Codex Harness currently gathers observations from two sources after running
`codex exec --json` in the configured checkout.

First, the runtime parses JSONL from the Codex process standard output. This
provides the thread reference, completion text, diagnostics, token usage, and,
when Codex emits them, the effective model and reasoning effort.

Second, the runtime uses the thread reference to search `CODEX_HOME/sessions`.
When `CODEX_HOME` is unset, it uses `~/.codex`. It finds a matching rollout
file, parses a `turn_context` record, and uses its `model` and `effort` values
to enrich the result.

The second source is a local Codex session-file layout. It is not part of the
runtime's configured checkout, configuration directory, or HTTP API contract.

## Current Flow

The current sequence is:

```text
codex exec --json
    |
    +-> standard-output JSONL -> parse thread, completion, diagnostics, usage,
    |                           model, and reasoning effort
    |
    +-> CODEX_HOME/sessions -> locate rollout by thread ID -> parse turn_context
                                                        -> enrich model and effort
```

For example, Codex may emit this standard output:

```json
{"type":"thread.started","thread_id":"0199a213-81c0-7800-8aa1-bbab2a035a53"}
{"type":"turn.completed","usage":{"input_tokens":10,"output_tokens":3}}
```

The runtime then searches for a path resembling:

```text
~/.codex/sessions/2026/10/05/rollout-2026-10-05T10-00-00-0199a213-81c0-7800-8aa1-bbab2a035a53.jsonl
```

It expects a record resembling:

```json
{"type":"turn_context","payload":{"model":"gpt-5.1-codex","effort":"high"}}
```

When a public `thread.started` or `turn.started` event already includes
`model`, `reasoning_effort`, or `effort`, the session scan is redundant for that
turn.

## Why This Matters

The session lookup is best effort and does not normally prevent a Codex turn
from completing. Its implications are nevertheless significant:

* The runtime depends on Codex's private directory hierarchy, rollout filename
  convention, and persisted event shape.
* A Codex upgrade can preserve normal execution while silently changing or
  removing the metadata enrichment path.
* The runtime reads a location outside its explicit configuration and checkout
  boundaries.
* Reproducibility depends on state generated by a prior or current local CLI
  process rather than only on the runtime input and process output.
* Tests must create realistic private session layouts to verify a result field
  that may be available from public process output.

## Docker Impact

Authentication and session persistence are separate concerns. A container may
authenticate successfully and execute Codex while the `sessions` directory is
absent, ephemeral, or located somewhere the runtime does not inspect.

The current implicit behavior encourages an operator to expose all Codex state
to a container merely to preserve optional model and reasoning-effort metadata:

```sh
docker run --rm \
  -v "$HOME/.codex:/home/runtime/.codex" \
  looping-louie-runtime:codex
```

That mount has avoidable drawbacks:

* It grants access to more host state than the runtime needs for its checkout.
* Its destination must match the container user's home directory, or
  `CODEX_HOME` must be set consistently.
* Ephemeral containers need durable session storage even when the session data
  has no role in executing the turn.
* Authentication, CLI settings, and session history become one opaque mounted
  filesystem contract.

The desired normal Docker deployment has only the intentionally required
runtime mounts:

```sh
docker run --rm \
  -v "$CONFIG_PATH:/runtime-config" \
  -v "$CHECKOUT_PATH:/workspaces/project" \
  looping-louie-runtime:codex \
  --config /runtime-config/runtime.json
```

This example does not prescribe an authentication mechanism. Authentication
must follow the supported non-interactive flow of the pinned Codex release and
remain separate from optional session observation.

## Proposal

### Preferred Option: Public JSONL Only

Establish the public JSONL fields emitted by each supported pinned Codex CLI
release. When `thread.started` or `turn.started` consistently reports the
effective model and reasoning effort, treat standard output as the sole source
of turn observations and remove the session-file scan.

The result behavior becomes:

* Use the streamed effective model when provided.
* Use streamed `reasoning_effort` or `effort` when provided.
* Fall back to the API-requested model when Codex does not report an effective
  model.
* Leave reasoning effort absent when Codex does not report it.

This leaves the Harness result correct without any dependency on `CODEX_HOME`
or a writable persistent session directory.

### Contingency: Explicit Optional Enrichment Adapter

If a required supported Codex version does not expose a needed field in public
JSONL, session inspection may remain available as an optional adapter. It must
not be an implicit behavior in the core executor.

The design boundary is:

```text
Codex standard-output JSONL -> core observations -> checkpoint result
Codex session directory ----> optional adapter -> additional metadata
```

The adapter needs an explicit session-root configuration. If deployment needs
session persistence, it should mount only a dedicated directory:

```sh
docker run --rm \
  -v "$CONFIG_PATH:/runtime-config" \
  -v "$CHECKOUT_PATH:/workspaces/project" \
  -v "$CODEX_STATE_PATH:/var/lib/codex" \
  -e CODEX_HOME=/var/lib/codex \
  looping-louie-runtime:codex \
  --config /runtime-config/runtime.json
```

The core result must remain valid when the adapter is disabled, its configured
directory is missing, the session file is absent, or its content is malformed.
The only effect may be omitted optional metadata; it must never fail the
Harness turn.

## Scope

This future work includes identifying supported Codex CLI JSONL contracts,
changing observation ownership, updating unit and integration tests, and
documenting deployment requirements.

It does not implement Docker images, change the configured checkout model, or
redesign Codex authentication. Those concerns are tracked separately by the
Docker Harness Images backlog item.

## Open Decisions

* Which Codex CLI versions does the runtime support, and which JSONL fields do
  they guarantee?
* Is effective reasoning effort required in the persisted Harness contract, or
  is it optional telemetry?
* If session enrichment remains, what configuration selects it and what
  lifecycle owns its directory?
* Can authentication state and session state be stored separately for the
  selected Codex CLI version?

## Acceptance Criteria

* The supported Codex version's JSONL contract is captured in tests or pinned
  fixtures.
* A Codex turn succeeds and reports all available public JSONL observations
  without a `CODEX_HOME` or session-state mount.
* Missing, inaccessible, malformed, or incompatible session files cannot fail a
  Codex turn.
* The result uses the requested model when Codex does not report an effective
  model.
* Any retained session enrichment is explicitly configured, optional, and has
  tests for absent and malformed data.
* Docker documentation states whether session storage is unnecessary or how an
  optional dedicated session mount is configured.

This backlog item records future work only; it does not request an immediate
runtime behavior or deployment change.
